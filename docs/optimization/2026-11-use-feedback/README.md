# 实际使用反馈驱动的优化准备

日期：2026-11-02。对象：AstroFairy 0.1.0a1。阶段：方案制定前的定形、盘点与供料。
准备结论及独立检查见[准备验收](readiness.md)。

## 本次要准备什么

维护者初步试用后报告调用不够方便、加载后流程执行不完整和多文件交付绕行；随后提出
主技能必要信息不足、预算过紧、检索能力不足等设计疑问。试用数量、宿主、模型、安装方式及
完整执行轨迹尚未提供。这是一次真实的维护者初步反馈，不能写成团队长期使用结论。

本轮获准在本项目内准备优化材料。产品运行代码、skill 正文、公开安装命令、依赖、预算与
旧评测基准均不改变；不安装新宿主插件、不调用业务模型、不提交、不推送、不发布。
局部程序复现只使用独立临时状态，不能代替原始使用轨迹、模型遵循评测或真人体验。

## 设计方向：先固定评价目标

1. **机制轻量**：职责清楚，接口一致，普通任务无需成员自己组织流程；允许必要资源投入。
2. **执行信息充分**：常规必需信息应可靠到达执行者；外置文件存在并不证明其已被读取。
3. **真实工作优先**：协议应自然表达合理任务，包括多文件成果、要求变化和必要澄清。
4. **成果与依据贯通**：可检查实际内容和组织理由；登记完整、调用成功、格式通过均不等于业务质量优秀。
5. **学习以复用效果闭环**：成功、纠正、反馈和重复任务均可供学习；保存、验证、发现、读取、适用判断及后续收益相互连接。
6. **核心职责稳定**：经验、工具和工作流在外围增长；正文长度与代码行数仅提供规模信号，不能替代职责判断。
7. **成熟方案为地板**：区分格式规范、宿主合同、作者实践、成熟实现和本项目策略；权威来源不作全系统达标证明。
8. **适度投入、有限收敛**：以有代表性的正常路径、原症状和关键失败路径验证；不把无止境边界穷举当作优化前提。

以上是维护者已明确的方向。具体实现仍需比较，不能把扩大全部上限、引入某一向量库、
主文整体搬入、接管宿主工具等具体做法直接写成已批准的方案。

## 本轮方法与角色

采用 FDP 的定形与供料纪律，属于后续概念优化设计的准备；本轮不是正式全量设计复核的结案，
也不是实现修复。执行者为当前工作代理，独立检查者在准备验收中记录，最终裁定者为维护者。
独立检查只验准备材料、证据解释和覆盖，不代替维护者批准未来技术方案。

下一步按 investigations.md 的依赖顺序形成可比较的方案，先确定正常任务的信息路径和
完成条件，再设计交付模型、资源策略与检索/学习接线；方案须附权威依据、必要性、影响域、
验证计划和明确代价。不得先按某个固定行数或工具品牌倒推需求。
