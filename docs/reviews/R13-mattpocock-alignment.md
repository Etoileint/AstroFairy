## 主要判断

**借鉴成立，不等于照搬完整流程，也不证明已取得相同或更好的实际效果。**

两项重要差异应持续明确：Matt 当前 grilling 会整轮询问已经可问的决策，并等待确认；
星灵按用户目标采用可逆默认、记录假设、少问关键问题。Matt 以工程人员可选择和组合的技能为主，
星灵把大部分组织责任交给智能体。这些差异有用户依据，不因与上游不同就成为缺陷。

Matt 的 retro 是环境改进建议，teach 是人类教学流程；它们没有提供可直接替换本项目的自动学习运行器。
星灵的候选、验证、采用、版本和退役是本项目设计，仍须接受成熟实现比较和学习效果验证，不能借作者名义免审。

## 反向查漏与不采用事项

从上游 SCOPE、术语和写作指南重新检查，而不是只沿用初版选择的亮点：

- **人类 agency**：上游明确把人类选择/记忆视作值得支付的成本；星灵将普通组织交给智能体，只保留重要决定。
  这是产品目标差异；不能把“极低负担”包装成对上游所有交互哲学的遵循。
- **提问上限**：上游 `.out-of-scope/question-limits.md` 明确拒绝固定数字上限。星灵的 `MAX_QUESTIONS=3`
  是自己的策略，不能归功于 grilling；是否截断必要澄清，由 R03/R06/R07 用任务实测判定，本轮不直接移除。
- **厂商问题工具**：上游不把某家原生问题 UI 写入通用技能。星灵公共入口也不命名厂商工具，ask 是自己的本地协议，
  宿主如何呈现问题仍由宿主决定；没有承诺所有宿主都免确认或具有同样 UI。
- **递归与宿主边界**：上游把子代理递归限制交给 harness。星灵也不托管通用子代理服务；不能因有本地预算就声称限制了所有宿主调用。
- **修剪要看行为**：上游 no-op/重复检测强调运行后的效果，不是只数行数。入口预算与 source-of-truth 查询有价值，
  仍不能证明核心长期不膨胀；R02-D02 的工作包问题继续保留。
- **学习与示例泛化**：上游写作指南反对把单次 run 的特例当通用方法。候选验证结构有帮助，但合成样例和一两次成功
  不足以证明成熟；需要 R08–R10 的相邻负例、重复任务和增长试验。
- **维护范围**：SCOPE 的 observed-failure 门是作者接受仓库改动的治理规则，不能据此把星灵学习限制为只收错误。
  同样，工程 tracker、课件库、代码测试接口确认、所有 prototype 分支都没有理由成为普通任务的强制前置。

这些额外实践形成后续判据，不因上游有一项政策就自动给本项目新增常驻规则或改动核心。
