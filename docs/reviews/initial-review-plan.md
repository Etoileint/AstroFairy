## 1. 复核目标与依据

复核回答：星灵是否以足够简单、通用、轻量且可持续的机制，实现低负担的任务委托、可靠交付和经验复用？
检查对象包括产品定位、设计、脚本、skill 指令、实际行为、资产生命周期、分发及对外承诺。
现有模块划分、代码和文档均可被质疑；已有实现不自动构成需求或正确性依据。

依据分层：

1. **用户愿景与明确约束：** 判断产品是否解决了正确的问题，优先于参考实现的习惯。
2. **适用的行业规范和宿主契约：** 判断格式、安装、发现和接口是否成立，回到一手来源核验。
3. **Matt Pocock 的参考实现：** 判断研究是否准确、借鉴是否有效、差异是否有理由；不将其全部选择升格为强制规范。
4. **本项目声明：** README、ADR、架构文档和 skill 描述中的每项承诺都需要实际支撑。
5. **实现与观测证据：** 源码、反例、执行记录和实际成果用于支持或否定上述主张。

行业依据必须回到标准发布机构、原作者、项目官方仓库和官方文档，按[权威来源规则](review-record-template.md)取证。
二手内容和模型记忆只提供线索。官方目录页、摘要页、产品自述、源码和实际测量的证据强度分别标记。
每项事实引用保存版本、定位、取得时间及所支持的主张；没有取得全文的标准不宣称条款级合规。

行业规范、参考实现和产品效果分别出结论。参考校验器通过、安装成功、宿主正确执行和成果可用，分别取证。
完整性以本节愿景、已声明能力和第 6 节行为类别为范围；新增类别、未覆盖组合和未决前提显式登记。
长期可持续性采用结构论证、增长试验和演化演练支持，保留尚未观察到的时间跨度。

## 3. 执行与判断规则

每轮选一个主要方面，先明确适用范围，再取证、尝试反例、形成发现、核验发现真实性，最后给出有限范围的结论。
架构、标准、参考实现和实际行为的复核深度分别安排；本轮不展开实际审计或修复。

每个检查项的结论为：**通过 / 不通过 / 待证 / 不适用**。
不适用需要理由和边界；待证需要缺少的证据及其对产品判断的影响。现有测试未覆盖的项目保持待证。
证据注明属于结构分析、机械实测、宿主行为、模型判断或真实用户反馈，并绑定源码或产物版本。

发现分级：

- **P0 根本阻断：** 否定核心愿景或破坏关键真实性交付保证，需要先处理。
- **P1 实质缺口：** 明显影响质量、使用负担、通用性、可移植性或长期演化。
- **P2 局部问题：** 在已明确的局部条件下影响可用性或维护。
- **P3 可选改进：** 有潜在收益，尚不足以成为基线义务。

评级结合发生条件、影响、可检测性和已有缓解，不按检查项数量计算总分。
单项完成需有逐项结论、证据索引、真实问题与撤回理由、剩余不确定性、最小改进建议及影响范围。
修复进入后续安排，已有明确授权时按授权范围执行；修复后仅重验受影响方面和必要的集成路径。
判断性较强的架构结论和行为效果，安排与主审假设隔离的独立复验；准备阶段不启动额外执行者。

正式设计复核采用 FDP 复核支线的取证、发现真实性复查、独立复验与有边界收口纪律。
实际代码、宿主行为、性能与质量仍需分别取证。方法本身不作为外部行业达标证据。
执行前回读维护者提供的现行方法原件；角色、项目记录落位与适配声明见[轮次记录模板](review-record-template.md)。
原 P0–P3 保留为本项目处置优先级；正式发现另记 BLOCKER/CRITICAL/MAJOR/MINOR/NOTE 严重度，
逐条说明影响依据与优先级映射，不将两种刻度混为同一分类。

### 全对象共同完成的行业对标检查

以下 Q01–Q08 逐一应用于每个 A/M/C/U 对象，与 R01–R16 交叉执行，共同形成总清单。
未发现适用的正式标准时，仍须调查成熟设计与实现并说明依据，保持该对象的对标义务。

| 编号 | 每个对象必须回答的问题 | 完成证据 |
|---|---|---|
| Q01 | 该对象的职责、必要性、前提和承诺是什么？ | 愿景关系、输入输出、责任边界、删除/替换影响及当前实现定位。 |
| Q02 | 权威规范、设计与成熟实现有哪些，哪些适用？ | 一手来源、固定版本/摘要、具体条款或符号位置、适用理由和访问限制。 |
| Q03 | 已比较哪些合理备选方案？ | 包括复用、组合、宿主原生能力及自有实现；说明检索范围和有理由排除的候选。 |
| Q04 | 相同职责和前提下，关键地板与实际差异是什么？ | 保证、正确性、恢复、权限、质量、资源、维护及演化维度；基础保证与功能规模分别评价。 |
| Q05 | 当前实现达到或超越的主张如何证成？ | 结构论证、代码证据、反例与可复现试验；超越限定比较对象和维度，无法证明则待证。 |
| Q06 | 整体连接后是否仍保有这些保证？ | 依赖、权限、数据、异常、版本及扩展路径的组合证据，关联 C 对象。 |
| Q07 | 有无误判、证据缺口或遗漏责任？ | 换攻击起点重推、逐行覆盖声明、独立主体复验及撤回理由。 |
| Q08 | 最终保留、复用、替换、简化或重设计如何决定？ | 决策理由、影响、处置优先级、剩余未知与重验范围；全对象状态不得静默省略。 |

## 4. 分方面详细清单

以下所有编号初始状态均为待复核。“所需证据与判据”描述未来应取得的证据，不代表目前已取得。

### R01 愿景、任务范围与产品承诺

| 编号 | 复核问题 | 所需证据与判据 |
|---|---|---|
| R01-01 | 愿景是否被准确整理？ | 对照用户要求与 V01–V17，列出原要求到产品承诺的关系；无自行添加的重型目标或遗漏。 |
| R01-02 | 目标用户与人机分工是否准确？ | 用首次使用、提出任务、变更要求和审核成果四条旅程检验；组织负担由智能体承担。 |
| R01-03 | 通用性的边界是否明确？ | 按输入、输出、工具依赖、判断和副作用分类；支持范围有依据，开放残类在册。 |
| R01-04 | 是否把高投入工程要求扩散到普通工作？ | 比较低风险短任务与复杂任务的实际步骤；检查和留痕投入与收益相称。 |
| R01-05 | “可用至优秀”是否可评价？ | 各任务先明确最低可用条件、关键错误和质量提升维度；质量判据先于成果打分确定。 |
| R01-06 | 可用、完整和完美是否被混淆？ | 检验交付策略与停止条件；允许诚实的部分结果，禁止以格式齐全替代内容可用。 |
| R01-07 | 每项外部承诺能否找到支持？ | 建立承诺到机制、测试和观测的对应；超出证据范围的承诺标记待证或建议收窄。 |

### R02 核心架构的必要性、职责分离与覆盖

| 编号 | 复核问题 | 所需证据与判据 |
|---|---|---|
| R02-01 | 架构从哪些基本问题和前提推出？ | 从任务目标、行动、观测、判断、交付及学习需要推导职责；声明协作宿主、授权和持久化前提。 |
| R02-02 | 每项核心职责是否必要？ | 逐项做删除或合并试验；能指出消失的能力或转移的复杂度，不以现有文件数量自证。 |
| R02-03 | 职责之间是否独立且边界清楚？ | 建立职责、输入、输出、权威和依赖图；同一决定有唯一负责者，共享数据有明确所有权。 |
| R02-04 | 对声明的任务范围是否有缺口？ | 用第 6 节行为类别推演目标到交付；不能落位的责任登记为缺口，不用扩大已有模块名称遮盖。 |
| R02-05 | 核心与任务策略是否分离？ | 增加一个新任务类型和新工作流；需要改动的核心规则与原因逐项可解释。 |
| R02-06 | 四步入口与内部机制是否一致？ | 跟踪 Define/Produce/Check/Deliver 到实际控制流；内部复杂度有作用，用户流程无隐含额外阶段。 |
| R02-07 | 当前运行器的复杂度是否值得？ | 对状态机、SQLite、事件链、内容寻址、调用包装分别比较更小方案；以不变量和实际成本选择。 |
| R02-08 | 扩展点是否真实而可替换？ | 替换工具、检查器、资产策略和宿主的演练；协议不暗含具体格式、工具或单个模型。 |
| R02-09 | 能否诚实说明架构保证范围？ | 列出推导依赖、已知残类和反例；行数预算与少量成功样本不作为永久充分性的证明。 |

### R03 用户体验、引导与自主推进

| 编号 | 复核问题 | 所需证据与判据 |
|---|---|---|
| R03-01 | 第一次使用需要多少人工组织？ | 新环境、仅有 brief 和材料的试用；记录用户需理解的术语、选择和配置，分别归属管理员或成员。 |
| R03-02 | 模糊需求能否直接推进？ | 事实可查和选择可逆的任务；智能体自行调查并记录假设，不向用户索取可自行获得的信息。 |
| R03-03 | 问题是否少而关键？ | 同时试验关键缺口和非关键缺口；问题易回答、有推荐，必要的问题得到回答后才执行依赖动作。 |
| R03-04 | 智能体是否承担方法与任务管理？ | 检查是否要求用户选择流程、维护编号、写规格、填写 JSON 或自行选资产；正常路径可直接委托。 |
| R03-05 | 变更、否定和反馈是否自然？ | 通过普通语言插入新约束、纠正和偏好；用户无需先认识内部命令，变化能进入当前工作。 |
| R03-06 | 推进信息是否及时而有用？ | 记录首个可见反馈、关键进度说明与等待时长；消息表达结果、假设或阻塞，而非内部流程堆叠。 |
| R03-07 | 能否方便结束、重做和继续？ | 完成、取消、部分交付和跨会话继续的实际操作；用户能找到成果及下一步，避免反复初始化。 |

### R04 任务协议、执行一致性与恢复

| 编号 | 复核问题 | 所需证据与判据 |
|---|---|---|
| R04-01 | 协议语义和字段是否一致？ | CLI、生成 schema、Python API、指令和错误回包对照；未知字段、重复键和非法值有明确结果。 |
| R04-02 | 要求来源是否被正确保存？ | 显式要求、派生准则、运行策略和后续输入分别演练；派生判断不能无依据地改写用户要求。 |
| R04-03 | 状态转移是否覆盖合法与非法路径？ | 建立转移表并运行反例；关闭、待答、待调用、失败和预算耗尽的规则不冲突。 |
| R04-04 | 调用记录与实际效果能否对应？ | 在动作前后分别模拟中断；尚未确定的效果保持不确定，避免重复执行或伪造成功。 |
| R04-05 | 并发、重复和过期输入如何处理？ | 同序号提交、迟到报告、重复报告及多进程竞争；拒绝或合并规则一致，未发生静默覆盖。 |
| R04-06 | 持久化是否保真并可恢复？ | 原始字节、编码异常、数据库/内容损坏和重启；完整性错误可见，恢复不修改既有事实。 |
| R04-07 | 生命周期结束与迟到信息是否协调？ | 关闭后反馈、回执重导出和迟到结果；停止新工作、保留历史与更新投影的语义可解释。 |

### R05 成果质量、验收与可分析性

| 编号 | 复核问题 | 所需证据与判据 |
|---|---|---|
| R05-01 | 验收标准是否真的代表任务成功？ | 从请求与材料独立导出准则，再对照智能体标准；必要内容、受众、格式及关键限制被覆盖。 |
| R05-02 | 默认检查是否会制造虚假通过？ | 非空但错误、格式正确但答非所问的成果；不能仅靠文件存在或模型一句自评达成实质验收。 |
| R05-03 | 实际检查对象与交付物是否相同？ | 比较引用、字节、版本和导出文件；检查摘要、旧版本或中间稿不得充当最终成果检查。 |
| R05-04 | 事实、推导与建议能否区分？ | 从最终成果逆向抽查数值、引用、结论和行动建议；能回到材料或明确的推导，限制有说明。 |
| R05-05 | 审核者能否理解内容组织？ | 让不参与制作的人依据成果与回执说明结构、关键选择和取舍；记录重建成本及仍需猜测的部分。 |
| R05-06 | 判断的主体和强度是否真实？ | 工具检查、宿主动作、模型审查和用户反馈逐项溯源；既不伪装独立验收，也不遗漏实际执行证据。 |
| R05-07 | 冲突、失败和未知能否影响结论？ | 正反审查、缺失依赖、未渲染文件及未解决调用；无法通过追加无根据的 pass 消除问题。 |
| R05-08 | 成果组合是否满足通用交付需要？ | 单文件、多文件、可编辑源件与预览的任务；主成果、附属成果和回执可定位，必要内容不遗落在工作区。 |

### R06 确定性脚本与模型判断的职责

| 编号 | 复核问题 | 所需证据与判据 |
|---|---|---|
| R06-01 | 哪些重要保证实际由代码执行？ | 建立保证到执行点、调用通道和失败结果的映射；仅写在指令中的要求标明其约束强度。 |
| R06-02 | 机械劳动是否仍交给模型反复组织？ | 观察字段拼装、路径管理、资料索引、回执制作和状态维护；识别可脚本化且有净收益的重复动作。 |
| R06-03 | 脚本是否僭越语义判断？ | 检查自动准则和状态判定；有限语法检查不自动推导事实可靠或内容优秀。 |
| R06-04 | 模型能否轻易绕过所声明的保证？ | 从模型实际可用工具逐通道检查；执行边界写清楚，协作式约定不被描述成强制沙箱。 |
| R06-05 | 模型是否必须理解过多内部协议？ | 记录一次交付的协议推理、修错和工具发现成本；机械机制确实降低而非转移模型负担。 |
| R06-06 | 机器规则是否与文本单源同步？ | 改动一个字段或规则追踪全部消费者；schema、帮助、文档和错误语义没有竞争性权威。 |
| R06-07 | 缺工具时是否合理降级？ | 环境缺少制作、渲染或检查工具的任务；发现能力边界、采用有依据的替代，明确未完成部分。 |

### R08 学习回流与使用者进步

| R08-07 | 用户是否逐渐更会表达和判断？ | 重复使用时观察关键问题回答、验收理解和简短说明的作用；保留证据，不将额外作业强加给用户。 |
| R08-08 | 回流机制是否实际可达？ | 从一次普通交付和真实反馈开始走到下一次受益；不要求用户额外触发复杂维护流程才发生任何改进。 |

### R09 资产库、工作流收敛与分享

| R09-07 | 分享包是否独立可用？ | 全新接收端只凭包导入、验证和执行；依赖、来源、许可及私有附件需求明确。 |

## 5. 建议复核顺序与每轮产物

所有方面保留稳定编号，按依赖与影响调整执行顺序：

| 阶段 | 顺序 | 目的 |
|---|---|---|
| 第一阶段 | R01 → R02 | 建立愿景判据，检验核心是否值得、是否覆盖目标；高层假设失效时先收敛方向。 |
| 第二阶段 | R11 → R13 | 核对行业契约与参考来源；必要时回到架构结论重判，不让误读来源进入后续假设。 |
| 第三阶段 | R04 → R06 → R05 → R14 | 核验实际协议、执行约束、成果与证据、授权和数据边界。 |
| 第四阶段 | R03 → R07 | 观察用户负担、自主推进、质量收益和实际速度。 |
| 第五阶段 | R08 → R09 → R10 | 检验经验回流、工作流复用和增长后的持续可用性。 |
| 第六阶段 | R12 → R16 → R15 终审 | 完成跨宿主/分发与公开承诺核对，复核整条证据链和集成效果。 |

R14 的权限边界、R15 的证据规则从第一轮即贯穿全程；表中的阶段仅指定集中结论轮次。
每轮默认只处理一个主要方面，以便充分取证并保持结论可读。跨面影响登记到对应编号，统一追踪。

每轮形成一份对应报告，至少包含：

1. 被审版本、范围、相关 V 编号、外部依据的版本和读取时间。
2. 逐项结论与证据引用；源码位置、产物引用和执行结果可回链。
3. 发现：触发条件、预期与实际、违反的依据、根因、影响、严重程度和最小建议。
4. 发现真实性复查、撤回项、独立复验结果及未决分歧。
5. 本轮结论、待证事项、对其他方面的影响和后续动作。

正式修复时记录改变了什么及影响哪些编号，保留前后证据。受影响项目重新判定，历史结论不被静默覆盖。

## 7. 收口条件与证据限制

整体复核结束时应同时给出：

- **愿景结论：** 哪些目标已被支持，哪些被否定，哪些仍待证；主要风险和适用范围。
- **设计结论：** 核心职责的保留/删除/合并/补足依据，关键前提及未闭合责任。
- **标准与参考结论：** 格式/宿主合规状态，以及 Matt 实践的采用、调整、遗漏和有意差异。
- **行为结论：** 对真实使用负担、交付质量、速度及学习收益的实际观察。
- **演化结论：** 增长试验和替换演练的结果、未来变化的吸收位置，以及未被证明的长期主张。
- **改进安排：** 必须修复、应优先改进、可选改进、无需变更与待证事项，各有依据和影响范围。

每个 V 编号和 R 检查项都有结论或明确待证项，跨面影响有去向；没有把开放问题当成已通过。
有问题即登记真实问题，没有问题则说明覆盖和证据；不为形成报告数量制造改动。
完整复核也不承诺枚举所有未来任务或证明永久无缺陷；结论绑定版本、前提、行为范围和证据强度。
